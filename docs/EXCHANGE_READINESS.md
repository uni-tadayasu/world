# MACHI REWARDS：原資管理と交換の検証

更新日: 2026-11-25

## 現在できること

設定 →「交換の準備状況を開く」で、実際の報酬と、価値のない検証用の交換を切り替えます。

**実際の円・Bitcoinを生成したり、無限に増やしたりする機能はありません。本番の交換・送金は停止中です。** 送金先は後から指定する方針のため、実アドレスを入力する画面はありません。外部サービスとの契約、ウォレット開設、資金購入・入金、登録申請も行っていません。

動作確認では、検証資金の補充、見積、申請、取消、検証上の完了を操作できます。検証上の完了は `simulated_paid` であり、ブロックチェーン取引や実送金を表しません。

## 残高と広告売上を分離

| 種類 | 管理場所 | 性質 |
| --- | --- | --- |
| ゲーム内所持金 | 端末の `life.state.money` | 初期所持金やセーブの金額。換金対象外 |
| 実際の報酬用の台帳 | `exchange_*` と `reward_treasury_*` | サーバーで確認した報酬・原資の記録。本番の交換は未接続 |
| 検証MR・検証sat | `exchange_sandbox_*` | 金銭的価値なし。本番台帳への移動・合算・換金不可 |
| スポンサー広告の注文・円建て売上 | `sponsor_*` | Stripeの署名済み決済通知による注文記録。決済手数料・返金・税・銀行への着金を反映した自由に使える資金や、BTCではない |

検証用の資金は何度でも補充できます。ただし有限の整数で管理し、保有上限を設けます。`Infinity` や巨大な数値を金融データとして受理せず、本番の原資を裏付ける値にも使いません。

## 独自の運用案

以下は `REWARD_TREASURY_POLICY` に固定した初期の**運用案**です。法的条件や資金の準備が完了したことを意味せず、現在プレイヤーへBTCを受け取る権利を約束するものではありません。

| 項目 | 運用案 |
| --- | --- |
| 名称 | MACHI REWARDS |
| 報酬の対象 | 日本在住・18歳以上で、受給資格を確認した利用者 |
| 通貨 | 無償の報酬MR。初期所持金からの変換、販売、利用者間譲渡はなし |
| 数量の基準 | 1 MR = 1 satoshi。円との固定レートは設定しない |
| 日次報酬 | サーバーで受給資格を確認した利用者1人につき、1日100 MR |
| 日付 | Asia/Tokyo の暦日。端末時刻は使わない |
| 最低申請額 | 10,000 MR |
| 1回の上限 | 100,000 MR |
| 原資 | 運営が事前に用意し、検証できた資金の範囲内 |
| 初期の実原資 | 0 satoshi |
| 手数料 | 本番は未確定。検証用の0という値を本番へ適用しない |
| 送金先 | 後から設定。現在は収集しない |

原資の調達方法としてスポンサー掲載枠の販売を準備しています。将来の広告収入、未購入の掲載枠、クライアントが申告した残高は入金済み資金として計上しません。ゲームへの訪問や操作の事実だけから、現実のお金が生まれるわけではありません。

スポンサー売上から資金を拠出する場合も、実際の円建て入金、決済手数料・返金・税・運営費などの支払義務、自由に割り当てられる予算を確認した後に、別途準備したBTCを検証する必要があります。広告の支払通知からBTC原資へ直接加算する経路はありません。購入受付は販売者情報と税・決済設定が整うまで停止中です。詳細は [SPONSORSHIP_OPERATIONS.md](SPONSORSHIP_OPERATIONS.md) を参照してください。

日次報酬は現在の公開HTTPから受給できません。内部サービスの `creditDailyReward()` は、接続先が確認した受給者ID、地域、年齢条件、有効期限を必要とします。Cookieを消して別プロフィールを作っても、同じ確認済み受給者の同日再受給を拒否する設計です。チェックボックス、クライアントの `verified:true`、位置やプレイ時間の申告は確認の代わりになりません。

## 本番原資の記録

`createRewardTreasuryService()` は次の境界を持ちます。

- `getState()`：記録済み原資、報酬に割り当てた数量、未割当数量を返します。
- `ingestConfirmedFunding(envelope)`：サーバーに接続した検証器の確認結果だけを記帳します。
- `creditDailyReward({userId, beneficiaryRef})`：確認済み受給者の日次報酬を、記録済み原資の範囲内で割り当てます。

入金確認結果には、正しい提供元、Bitcoinメインネット、6承認以上、正規化されたUTXO参照、正の整数satoshi、確認済みの原資受取先参照を要求します。同じ入金を再送しても増加は1回です。報酬の割当、日次受給、本番報酬イベントと台帳への記帳を、単一SQL文のトリガー内で処理します。途中で失敗すれば全体を取り消します。

**入金検証器は本番へ未接続です。** 公開HTTPは `verifier:null` を使います。ブラウザや環境変数の有効化フラグから検証器を差し込むことはできず、原資や実報酬を自由に増やす公開APIもありません。

台帳上の累計入金は、ウォレットの現在の未使用残高を保証しません。実接続時には、自社が支配する資金であること、純増の入金であること、釣銭出力の二重計上除外、出金、チェーン再編、未使用残高の継続照合が必要です。これらを省いて本番の支払いを有効化しないでください。現在のコードに実送金dispatcherはありません。

## 検証専用の操作

「動作確認」タブは常に、実際のBTCを受け取れないことを表示します。

1. 検証資金の補充ボタンで10,000検証MRを追加します。
2. 数量を入力して5分間有効な検証見積を取得します。
3. 数量と固定の「検証用の受取先」を確認し、申請します。
4. 申請の予約残高を確認します。
5. 取消または明示的な検証完了を実行します。完了なら予約分を一度だけ消費し、取消なら一度だけ返します。

検証ルールは、最低1,000 MR、1回最大1,000,000 MR、1 MR = 1検証sat、検証手数料0です。残高上限は1兆検証MR、補充間隔は1.5秒です。上限に達したときは、検証完了で残高を減らしてから補充できます。

本番用とは別のテーブル・見積・申請・台帳を使います。実アドレス、秘密鍵、シードフレーズ、本人確認書類は入力しません。外部への送金リクエスト、実取引IDの生成、検証資金を本番へ移す処理もありません。

## 公開API

すべて `/api/social` 配下です。既存のHttpOnly端末Cookie、同一オリジン検査、`X-Machi-User-Id`、POSTの `expectedUserId` を維持し、ゲームにログイン画面は追加しません。

| API | 動作 |
| --- | --- |
| `GET /exchange` | 実報酬・履歴・運用案・原資の記録・準備状況。`available:false`、`canPay:false` |
| `GET /exchange/requests` | 当該ブラウザの実報酬の申請履歴 |
| 本番の見積・申請・取消POST | `503 exchange_unavailable`。送金は実行しない |
| `GET /exchange/sandbox` | 検証残高、検証申請、検証ルール |
| `POST /exchange/sandbox/refill` | 再送防止キーを付けて固定10,000検証MRを補充 |
| `POST /exchange/sandbox/quote` | 検証数量の見積 |
| `POST /exchange/sandbox/requests` | 見積IDと再送防止キーで検証申請 |
| `POST /exchange/sandbox/requests/:id/cancel` | 未完了の検証申請を取消 |
| `POST /exchange/sandbox/requests/:id/complete` | 未完了の検証申請を検証上の完了へ移す |

検証の全成功応答は `mode:"sandbox"`、`network:"simulation"`、`realValue:false` と所有者IDを返し、クライアントでも検査します。検証POSTは端末ごとに60回/分、500回/時までです。状態の読取は、操作上限に達した場合も利用できます。

補充と申請の応答が不明な場合は同じ再送防止キーを保持し、新しいキーで無条件に再実行しません。画面を閉じる、タブを変える、ブラウザIDが変わる場合は古い応答と見積を無効化します。

## 実運用に残る作業

実際の資金、入金検証・送金の接続先、受給資格と送金先の確認、端末紛失時の回復、提供地域で必要な手続を整える必要があります。原資と送金先だけを入力すれば全てが完了する状態ではありません。

日本向けのサービスについては、無料ポイントや自社原資というだけで登録不要とは断定できません。金融庁のガイドラインは、オンラインゲームの取引画面を含む一連の行為から媒介該当性を判断する考え方を示しています。独自のソフトウェアを作成したことと、登録や事業開始の条件を満たしたことは別です。

- [金融庁：暗号資産・電子決済手段関係](https://www.fsa.go.jp/policy/virtual_currency02/)
- [金融庁：FinTechサポートデスク](https://www.fsa.go.jp/news/27/sonota/20151214-2.html)
- [金融庁：事務ガイドライン・暗号資産交換業者関係](https://www.fsa.go.jp/common/law/guide/kaisya/16.pdf)

この文書は登録・契約・適法性の確認を行った証明ではありません。現在は外部の交換・送金事業者との契約や、本人確認書類の収集を行っていません。

## 検証の考え方

実SQLiteで、入金再送、受給者の日次制限、原資不足、同時申請、二重完了、取消との競合、書き込み失敗時のロールバックを確認します。検証を何度行っても本番台帳が変わらないことも確認します。外部検証器はテスト用の確認結果を使用し、本物の原資や暗号資産を送金する試験は行いません。
